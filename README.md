# Koreahospital

Koreahospital 是一个本地优先的医院社交媒体运营工作台，用来把“选题、内容生产、审核、人工发布、数据回填和复盘”串成一条可追踪的工作流程。

当前首版主要服务 Koreahospital 一个项目和一名运营人员，重点支持小红书图文与抖音短视频的内容闭环。系统可以辅助研究、写作、生成素材、审核和分析，但不会替你自动登录平台或发布内容。

## 快速开始

### 环境要求

- Node.js `>= 20.9.0`
- npm
- 如果使用真实模型，需要对应服务商的 API Key
- 如果使用 R2 素材存储，需要安装并登录 Wrangler；不配置 R2 也可以使用本地素材存储

### 安装并启动

```bash
git clone <仓库地址>
cd Koreahospital
npm install
npm run dev
```

启动后打开：<http://localhost:3000/workbench>

首次运行时，程序会自动创建 `data/` 目录、SQLite 数据库和基础种子数据。没有配置真实模型时，系统可以使用内置 Mock 模型启动和浏览界面。

生产模式可以这样运行：

```bash
npm run build
npm start
```

## 本地使用

### 第一次打开先检查这三处

1. 打开“项目简报”，确认医院定位、目标人群、品牌语气、转化目标和医疗禁区。
2. 打开“账号矩阵”或“账号定位”，确认小红书、抖音账号及其内容定位。
3. 打开“系统设置”，检查 Agent 模型、图像/视频模型和当前访问模式。

### 页面入口

| 目标 | 页面 |
|---|---|
| 查看今天要做什么 | `/workbench` |
| 编辑项目简报 | `/project` |
| 研究平台信号 | `/contents/research`、`/signals` |
| 管理选题 | `/topics` |
| 生成文案或脚本 | `/contents/ai` |
| 生产、审核、生成发布包 | `/production` |
| 管理素材和授权 | `/assets`、`/assets/upload` |
| 排期和查看待发布 | `/calendar`、`/today` |
| 内容数据和帖子分析 | `/data/posts` |
| 导入数据 | `/data/posts/import` 或 `/data/input` |
| 查看复盘报告 | `/data/reports`、`/review` |
| 配置模型与权限 | `/settings` |

### 推荐的完整操作顺序

```text
项目简报 / 账号定位
  → 选题研究 / 人工确认
  → 母版简报
  → 小红书图文或抖音脚本
  → 准备素材和授权
  → AI 审核
  → 人工终审
  → 生成发布包
  → 人工复制到平台并发布
  → 系统标记已发布
  → 24 小时 / 7 天 / 30 天回填数据
  → 复盘并人工确认改进建议
```

负责人每天优先查看工作台上的这些待办：待确认信号、待人工审核、待生成发布包、待回填数据和待确认回写。

## 配置 AI 模型

模型配置通过页面完成，不要求把 Key 写进前端代码或提交到 Git。

1. 打开 `/settings/agent-models`，配置研究、策略、文案、设计、发布和分析等 Agent 的文本模型。
2. 打开 `/settings/media-models`，配置图片模型和视频模型。
3. 填写服务商、Base URL、模型名称和 API Key。
4. 使用“测试连接”确认模型可用，再回到内容生产页面使用。

建议先用 Mock 模型检查页面和流程，再配置真实模型进行实际生成。模型未配置、请求失败或返回空结果时，页面应显示失败原因，不会把失败伪装成已完成。

模型 API 只向浏览器返回“是否已配置”等状态，不返回完整 API Key。不要把 Key 写入 README、日志、截图、提交记录或客户端代码。

## 日常工作流程

### 1. 选题研究

在 `/contents/research` 或 `/signals` 中记录公开来源、标题、观察时间和证据摘要。AI 可以提出选题和内容结构，但新的信号必须由人工确认后，才能进入正式选题池或知识库。

### 2. 内容生产

每条内容分成两层：

- **母版简报**：受众、目标、核心事实、证据、合规说明和 CTA。
- **平台版本**：小红书的标题/正文/封面，或抖音的脚本/分镜/素材清单。

这样可以维护一份共同事实，再根据平台特点生成不同版本，避免同一内容在不同平台互相矛盾。

### 3. 审核与发布

AI 先检查医疗风险、证据和平台格式；人工再检查医学准确性、表达方式、品牌风险和素材授权。只有人工批准后，内容才可以进入待发布。

系统会生成发布包，但发布动作由运营人员完成：复制内容、打开平台、手工发布，然后回到系统标记已发布。系统不自动登录、不自动发布、不自动评论点赞，也不处理验证码。

### 4. 回填与复盘

发布后在 `/data/posts` 或对应数据页面回填真实数据：播放/浏览、点赞、收藏、评论、分享、私信、咨询、有效线索和预约等。建议分别记录 24 小时、7 天和 30 天窗口。

AI 可以根据发布快照和数据生成归因报告，但只能提出“待确认回写建议”。负责人确认后，建议才会更新选题、结构、CTA 或发布节奏；数据不足时应标记“暂不下结论”。

## 数据导入

支持单条录入，也支持 CSV 或从 Excel 复制表格后粘贴。

导入时的基本流程是：

1. 打开 `/data/posts/import` 或 `/data/input`。
2. 粘贴表格或选择 CSV 文件。
3. 检查系统自动识别的列名；识别不准确时手动映射。
4. 确认平台和账号能匹配已有账号矩阵。
5. 提交导入，查看新增和跳过的行数。

账号日数据按“账号 + 日期”做幂等处理，重复导入不会重复计算。上传记录只记录本次导入的行数、写入数和跳过数；删除上传记录不会删除已经写入的业务指标。

没有真实数据时不要填猜测数字，可以明确标记数据不足。

## 文件和数据保存位置

| 路径 | 用途 | 是否提交 Git |
|---|---|---|
| `src/app/` | 页面和 API 路由 | 是 |
| `src/components/` | React 组件 | 是 |
| `src/lib/` | 数据库、模型、Skill、存储和业务逻辑 | 是 |
| `skills/` | 本地运营规则和平台 Skill | 是 |
| `data/clinic.db` | SQLite 业务数据 | 否，运行时生成 |
| `data/*.json` | 运行时配置 | 否，运行时生成 |
| `public/uploads/` | 本地上传素材 | 否，运行时生成 |

`data/` 和 `public/uploads/` 包含本地业务数据或素材。升级代码、迁移数据库或尝试危险操作前，请先备份它们，尤其是 `data/clinic.db`。

### 可选的 R2 配置

不配置 R2 时，素材保存到 `public/uploads/`。如果需要同步到 Cloudflare R2，可以通过设置页面或运行环境配置以下变量：

```text
R2_BUCKET
R2_PUBLIC_BASE
R2_ENDPOINT
R2_ACCESS_KEY_ID
R2_SECRET_ACCESS_KEY
R2_REGION
```

R2 上传失败时，本地文件仍作为兜底；不要把这些变量的真实值提交到仓库。

## 安全边界

- 医疗内容必须区分事实、推断和未知信息，不能夸大疗效或承诺结果。
- 患者照片、术前术后图、诊疗过程和可识别病例信息按敏感素材处理；授权不完整时不能进入待发布。
- 不保存小红书、抖音等第三方平台密码。
- 分享工作台前，应在系统设置中启用登录和只读权限；当前项目默认面向本机或受控环境使用。
- `readonly` 访问模式会阻止写接口和模型调用，但允许读取页面数据。
- AI 不能最终批准发布，也不能直接写入正式知识库。

## 常见问题

### 页面能打开，但 AI 不能生成

先检查 `/settings/agent-models` 或 `/settings/media-models`：服务商、Base URL、模型名和 Key 是否完整，再点击测试连接。不同模型类型不能混用，例如文本模型不能直接承担图片生成。

### 上传素材后看不到

先检查 `public/uploads/` 是否生成文件，再检查素材库记录。如果配置了 R2，R2 同步失败不会阻断本地保存；查看终端中的 R2 错误信息即可定位。

### 重复导入会不会造成重复数据

账号日数据按账号和日期幂等写入，重复行会在上传结果中计为跳过。帖子分析导入还会根据平台、外部 ID、URL 等字段识别已有记录，导入后应检查新增和更新结果。

### 为什么系统不直接帮我发布

这是产品边界：系统只生成发布包并记录结果，运营人员手动复制发布，以避免保存第三方账号凭据、绕过平台风控或无人值守操作。

## 贡献代码

提交改动前请遵循以下原则：

1. 先确认改动对应的真实用户流程和完成条件。
2. 保留本地已有数据和未提交改动，不使用破坏性清理命令。
3. 涉及数据、权限、模型或医疗内容时，增加对应的专项测试或可复现检查。
4. 提交前运行类型检查、相关测试、生产构建和 `git diff --check`。
5. 不提交 API Key、患者隐私、运行时数据库、上传素材或本地配置文件。
